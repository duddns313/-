# 유리 나누기 (Glass Coop) — 기획서

**한 줄**: 부부가 폰 한 대를 사이에 두고 마주 앉아, 서로 다른 단서를 말로 주고받으며 격자를 납선으로 나눠 스테인드글라스를 복원하는 협동 논리 퍼즐.

**참고**: *The Artisan of Glimmith*의 "격자를 나누고 색을 채우는" 논리 퍼즐 감각 + 파이프 게임의 "이어져서 완성되는" 쾌감. 원작들은 1인용이므로, 협동 부분은 새로 설계한다.

**협동 설계 원칙**: 혼자 할 수 있는 걸 둘이 나눠 하는 건 협동이 아니다. **혼자서는 물리적으로 불가능한 수**와 **혼자서는 알 수 없는 정보**, 두 축으로 협동을 강제한다.

---

## ① 구성 요소 목록

| 이름 | 역할 | 형태 | 비고 |
|---|---|---|---|
| **격자(Grid)** | 퍼즐 판 | N×N 셀 (4×4 ~ 7×7) | 스테인드글라스 창틀 |
| **셀(Cell)** | 최소 단위 | 정사각 유리 조각 | 반드시 어떤 영역에 속해야 함 |
| **색점(Seed)** | 영역의 씨앗 | 셀 위의 색 원 | 영역당 정확히 1개 |
| **납선(Seam)** | 셀 사이 경계벽 | 셀과 셀 사이 선분 | 플레이어가 긋고 지움 |
| **이중납선(Double Seam)** | ★협동 전용 벽 | 굵은 금색 선분, 양 끝에 앵커 2개 | **두 손가락이 동시에** 눌러야 토글 |
| **영역(Region)** | 납선으로 둘러싸인 연결된 셀 묶음 | — | 완성 판정의 단위 |
| **단서패널(Clue Panel)** | 각 플레이어 전용 정보창 | 화면 위/아래 가장자리 | 각자 방향으로 180° 회전 |

색점 색상은 5종 고정: 🔵파랑 · 🔴빨강 · 🟡노랑 · 🟢초록 · 🟣보라 (스테인드글라스 팔레트)

---

## ② 퍼즐 규칙 (자원·경제 대체)

납선을 긋고 지워서 격자 전체를 영역들로 나눈다. **아래 3개를 전부 만족하면 완성.**

1. **모든 영역은 색점을 정확히 1개 포함한다** (0개도, 2개도 안 됨)
2. **영역의 크기(셀 수) = 그 색점에 지정된 숫자**
3. **모든 셀은 어떤 영역에 속한다** (어디에도 안 속한 셀 없음)

> 이 규칙은 실제 스테인드글라스 제작(납선으로 유리 조각을 나눔)과 그대로 대응한다. 테마가 장식이 아니라 규칙 그 자체.

**되돌리기**: 납선은 언제든 다시 눌러 지울 수 있다. 실패 상태·시간 제한·점수 없음 — 부부가 편하게 하는 게임이라 **패배가 존재하지 않는다.**

### ★ 정보 분할 (협동 축 1 — "혼자서는 알 수 없다")

| 보이는 것 | 플레이어 A (아래쪽) | 플레이어 B (위쪽) | 둘 다 |
|---|---|---|---|
| 격자·납선 현황 | — | — | ✅ |
| 색점 **위치** | — | — | ✅ |
| 색점 **색깔** | — | — | ✅ |
| 각 색의 **영역 크기** | ✅ (예: 🔵=4) | ❌ | — |
| **제약 카드** (확장) | ❌ | ✅ (예: "🔴는 가장자리에 닿는다") | — |

→ A는 크기를 알지만 배치 제약을 모르고, B는 반대다. **말을 해야만 풀린다.**

MVP는 A의 크기 힌트만으로 유일해가 나오게 설계하고, 제약 카드(B 패널)는 난이도 확장으로 추가한다. 단 **B 패널 자리는 MVP부터 화면에 존재**해야 한다 (나중에 레이아웃을 안 뜯게).

### ★ 이중납선 (협동 축 2 — "혼자서는 손이 모자란다")

- 퍼즐당 이중납선 2~4개. 해답에 **반드시 필요한 위치**에만 배치한다 (장식용 금지).
- 양 끝 앵커를 **250ms 이내에 동시에** 눌러야 토글된다.
- 한쪽만 누르면 그 앵커가 맥동(pulse)하며 "짝을 기다리는 중" 표시 → 상대가 어디를 눌러야 할지 시각적으로 알려준다.
- 손가락 하나로는 양 끝에 물리적으로 닿을 수 없도록 **앵커 간 최소 거리를 화면 대각의 35% 이상**으로 강제한다. (안 그러면 혼자 두 손가락으로 해버려서 협동이 무너진다)

## ③ 퍼즐 공급 · 난이도 곡선 (적 AI 대체)

적이 없는 게임이므로, "컴퓨터가 하는 일" = 퍼즐을 내주는 것.

| 단계 | 격자 | 영역 수 | 이중납선 | 목표 소요 |
|---|---|---|---|---|
| 튜토리얼 1~2 | 4×4 | 3 | 0 (규칙 익히기) | 1분 |
| 튜토리얼 3 | 4×4 | 3 | 1 (동시 터치 학습) | 2분 |
| 쉬움 4~7 | 5×5 | 4 | 2 | 3분 |
| 보통 8~13 | 6×6 | 5 | 3 | 5분 |
| 어려움 14~18 | 7×7 | 5~6 | 4 | 8분 |

**MVP는 손으로 설계한 18판 고정 팩.** 절차적 생성기는 만들지 않는다 — 이유는 **유일해 보장**이 어렵기 때문. 유일해가 아니면 "논리적으로 풀었는데 정답이 아니라고 나오는" 최악의 경험이 발생한다.

대신 **검증기**를 만든다: 각 퍼즐에 대해 모든 가능한 분할을 완전탐색해 **해가 정확히 1개인지 확인**한다. 이게 `self-check` 단계의 핵심 테스트 중 하나다. (7×7 완전탐색은 가지치기하면 충분히 빠르다)

## ④ 조작 체계

**입력은 멀티터치 전용.** 마우스는 개발·디버그용으로만 동작.

| 동작 | 조작 |
|---|---|
| 일반 납선 긋기/지우기 | 셀 경계를 한 번 탭 (토글) |
| **이중납선 토글** | 양 끝 앵커를 **동시에** 탭 (250ms 이내, 서로 다른 `pointerId`) |
| 영역 미리보기 | 셀을 길게 누르기(500ms) → 그 셀이 속한 영역이 하이라이트 |
| 되돌리기 | 각 패널의 ↺ 버튼 (양쪽에 하나씩) |
| 다음/이전 퍼즐 | 완성 후 나타나는 버튼 |

### ⚠️ 멀티터치 필수 처리 (안 하면 반드시 터짐)

1. **`touch-action: none`** — 캔버스와 조작 영역에 필수. 없으면 브라우저가 터치를 스크롤로 가로챈다.
2. **`<meta name="viewport" ... user-scalable=no>`** — 두 손가락이 가까우면 핀치줌으로 오인식한다.
3. **Pointer Events 사용** (`pointerdown/move/up/cancel`) — `touchstart` 계열보다 마우스와 통합돼 디버그가 쉽다.
4. **`pointerId`로 손가락 구분** — 동시 터치 판정의 전제. 동일 `pointerId`가 양 앵커를 누른 건 **동시 터치로 인정하지 않는다** (혼자 두 손가락 방지).
5. **`pointercancel` 처리** — 전화가 오거나 알림이 뜨면 터치가 취소된다. 대기 중이던 앵커를 반드시 해제해야 유령 상태가 안 남는다.

### 마주 앉기 (화면 방향)

폰을 **가로로 눕혀 두 사람 사이에 놓는다.** 화면을 상하로 나눠:
- 아래쪽 절반 = 플레이어 A 패널 (정방향)
- 위쪽 절반 = 플레이어 B 패널 (**180° 회전**)
- 가운데 = 공용 격자 (회전 없음, 양쪽에서 다 읽히는 중립 디자인)

색점은 방향성이 없는 원형이라 양쪽에서 똑같이 보인다. **숫자는 격자 위에 절대 쓰지 않는다** (한쪽에서 거꾸로 보이므로) — 숫자는 각자 패널 안에만.

## ⑤ 화면 구성 (UI)

```
┌─────────────────────────────────────┐
│  [B 패널 — 180° 회전]                │  ← 아내 쪽
│  제약 카드 / ↺ / 진행도              │
├─────────────────────────────────────┤
│                                     │
│        공 용  격 자  (Canvas)        │  ← 가운데
│     색점 · 납선 · 이중납선 앵커       │
│                                     │
├─────────────────────────────────────┤
│  [A 패널 — 정방향]                   │  ← 내 쪽
│  🔵4  🔴3  🟡5  ... / ↺ / 진행도      │
└─────────────────────────────────────┘
```

- **진행도**: "영역 3/5 완성" — 양쪽 패널에 동일 표시
- **완성 연출**: 납선이 금색으로 빛나고 각 영역에 유리 질감·빛 투과가 채워진다 → 완성된 스테인드글라스 창이 드러남 (`game-texture` 스킬 담당)
- **대기 표시**: 이중납선 앵커 한쪽만 눌렸을 때 그 앵커가 맥동 + 반대쪽 앵커에 화살표 힌트
- **패배 화면 없음.** 완성 화면만 존재.

## ⑥ 완료 기준 (체크리스트) ★

각 항목은 `self-check` 스킬에서 테스트 하나가 된다.

### 퍼즐 로직 (headless 테스트 가능 — DOM 없이)
- [ ] 납선을 토글하면 영역 분할이 즉시 재계산된다
- [ ] 규칙 3개를 모두 만족하면 완성 상태가 `true`가 된다
- [ ] 규칙 중 하나라도 어기면 완성 상태가 `false`다 (색점 0개 영역 / 2개 영역 / 크기 불일치 각각 검증)
- [ ] **18판 전부 해가 정확히 1개다** (완전탐색 유일해 검증)
- [ ] 18판 전부 정답 배치를 넣으면 완성 판정이 뜬다
- [ ] 되돌리기가 직전 상태로 정확히 복원한다

### 협동 메커니즘
- [ ] 이중납선은 앵커 하나만 눌러서는 토글되지 않는다
- [ ] 서로 다른 `pointerId` 두 개가 250ms 이내에 양 앵커를 누르면 토글된다
- [ ] 같은 `pointerId`가 양 앵커를 순차로 눌러도 토글되지 않는다
- [ ] 251ms 이상 벌어지면 토글되지 않고 대기가 해제된다
- [ ] `pointercancel`이 오면 대기 중이던 앵커가 해제된다
- [ ] 모든 퍼즐의 이중납선 앵커 간 거리가 화면 대각의 35% 이상이다
- [ ] 이중납선을 안 쓰고는 어떤 퍼즐도 완성할 수 없다 (해답 필수 경로인지 검증)

### 입력·화면
- [ ] 두 손가락이 서로 다른 셀 경계를 동시에 눌러도 둘 다 정상 처리된다
- [ ] 격자 위에 숫자가 하나도 렌더링되지 않는다 (거꾸로 보이는 문제 방지)
- [ ] B 패널의 텍스트가 180° 회전된 상태로 렌더링된다
- [ ] 페이지에서 핀치줌·스크롤이 발생하지 않는다
- [ ] 퍼즐 완성 시 완성 연출과 다음 퍼즐 버튼이 나타난다

### 품질
- [ ] 브라우저 콘솔에 에러·경고가 0건이다
- [ ] 실제 폰에서 두 사람이 1판을 끝까지 완성할 수 있다 (실기기 확인)

## 성능 상한

2D Canvas 게임이라 3D의 draw call 대신 다음을 예산으로 잡는다.

| 항목 | 상한 | 지키는 법 |
|---|---|---|
| 목표 프레임 | 60fps (최악 장면 55 이상) | 아래 준수 시 자연 달성 |
| 최악 장면 | 7×7 격자 + 동시 터치 4점 + 완성 연출 파티클 120개 | 이 장면에서 측정 |
| 프레임당 그리기 시간 | ≤ 8ms | 격자는 정적 레이어로 캐시, 변하는 것만 매 프레임 |
| 캔버스 레이어 | 3장 (배경 격자 / 납선·색점 / 연출) | 배경은 한 번만 그리고 재사용 |
| 텍스처 | 1k 유리 타일 3~4종 | `game-texture` 스킬, 절차적 생성 폴백 |
| 상태 재계산 | 납선 토글당 1회, ≤ 2ms | 영역 탐색은 flood fill, 7×7=49셀이라 저렴 |

파티클이 예산을 넘으면 정밀도를 올릴 게 아니라 **개수를 줄인다.**

## 기술 구조

- **빌드 도구 없음.** 단일 `index.html` + ES 모듈. 로컬 서버(`python3 -m http.server`)로 바로 실행.
- **2D Canvas.** Three.js 불필요 (격자 퍼즐에 3D는 과잉).
- **GitHub Pages 정적 호스팅** + PWA (홈 화면 설치 → 앱처럼 실행).
- 고정 타임스텝 루프는 연출용으로만. 퍼즐 로직 자체는 이벤트 구동.

### 폴더 구조

```
glass-coop/
  index.html
  css/style.css
  js/
    puzzles.js     18판 퍼즐 데이터 (격자·색점·크기·이중납선 위치)
    puzzle.js      ★순수 로직: 상태·영역계산·규칙검증  (DOM 무관 = headless 테스트)
    intent.js      ★의도 객체 정의 {type:'toggleSeam', seamId, by:'A'}
    input.js       Pointer Events → intent 변환 (동시터치 판정 여기서)
    render.js      Canvas 그리기 (격자·납선·연출)
    ui.js          A/B 패널, 회전, 진행도
    main.js        진입점
  textures/        유리 재질 (game-texture 단계에서 채움)
  scripts/
    verify.js      유일해 완전탐색 검증기 (개발 도구)
    simulate.js    headless 퍼즐 로직 테스트 (self-check 단계)
  design/plan.md   이 문서
```

### ★ 로직 / 입력 분리 (원격 멀티플레이 대비)

```
입력(input.js) → 의도(intent) → 로직(puzzle.js) → 렌더(render.js)
                    ↑
              여기에 네트워크를 끼우면 그대로 원격 협동
```

`puzzle.js`는 **오직 intent만 받아 상태를 바꾼다.** 브라우저 API를 일절 참조하지 않으므로:
1. Node에서 브라우저 없이 테스트된다 (`self-check` 스킬의 headless 시뮬레이션)
2. 나중에 intent를 WebRTC/PeerJS로 상대에게 보내면 **로직 코드를 한 줄도 안 고치고** 원격 협동이 된다

단, 이중납선의 "동시 터치" 판정은 원격에선 물리적으로 불가능하므로, 원격 모드에서는 **"둘 다 각자 앵커를 활성화하면 토글"**(시간 제한 없이)로 규칙이 완화된다. 이 분기를 `intent.js`에 미리 자리만 만들어 둔다.

**제외(2차)**: B패널 제약 카드 · 원격 멀티플레이 · 퍼즐 생성기 · 레벨 에디터 · 사운드

## 승인 요청

이대로 만들까? 특히 아래 3개를 봐줘:

1. **협동 방식** — 이중납선(동시 터치) + 크기 힌트 독점, 이 두 개면 "둘이 해야만 하는" 느낌이 날까?
2. **패배 없음** — 시간 제한·실패를 아예 없앴는데, 긴장감이 아쉬우면 넣을 수 있어
3. **18판 고정** — 생성기 대신 손으로 만든 18판. 금방 다 풀어버릴 것 같으면 늘리자
