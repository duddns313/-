# 유리 나누기 (Glass Coop) — 기획서

**한 줄**: 부부가 폰 한 대를 사이에 두고 마주 앉아, 혼자서는 손이 모자란 조작을 맞춰가며 격자를 납선으로 나눠 스테인드글라스를 복원하는 협동 논리 퍼즐.

**참고**: *The Artisan of Glimmith*의 "격자를 나누고 색을 채우는" 논리 퍼즐 감각 + 파이프 게임의 "이어져서 완성되는" 쾌감. 원작들은 1인용이므로 협동은 새로 설계한다.

---

## 협동 설계 원칙 (★ 이 게임의 뼈대)

**혼자 할 수 있는 걸 둘이 나눠 하는 건 협동이 아니다.** 협동은 두 가지 방식으로만 진짜가 된다.

| 축 | 원리 | 한 폰에서 | 각자 폰에서 |
|---|---|---|---|
| **손이 모자람** | 동시에 두 곳을 조작해야 함 | ✅ 진짜 (물리적으로 강제됨) | ❌ 불가능 |
| **정보가 모자람** | 각자 다른 단서만 앎 | ❌ **불가능** | ✅ 진짜 |

### 왜 한 폰에서 정보 비대칭을 쓰지 않는가

한 화면을 같이 보면 **화면에 그려진 건 둘 다 본다.** 180° 회전은 읽기를 불편하게 할 뿐 못 보게 막지 못하고, 거꾸로 된 글자는 조금만 신경 쓰면 읽힌다. 협동 게임에서 숨긴 정보는 부정행위를 막는 장치가 아니라 대화를 만드는 장치인데(같은 편이라 훔쳐볼 동기 자체가 없다), **훔쳐보기에 아무 노력이 안 들면 아무도 부정할 마음이 없어도 그냥 눈에 들어와서** 장치가 무너진다.

그리고 애초에 필요가 없다. **논리 퍼즐을 둘이 같이 들여다보는 것 자체가 이미 대화를 만든다** — "저기가 4칸이어야지" "그럼 이 선이 틀렸네". 억지 장치 없이 협동은 이미 거기 있다.

따라서 **한 폰 버전(MVP)의 협동은 전부 "손이 모자람" 축으로 간다.** 정보 비대칭은 각자 폰 모드(2차)에서 진짜로 도입한다.

## ① 구성 요소 목록

| 이름 | 역할 | 형태 | 비고 |
|---|---|---|---|
| **격자(Grid)** | 퍼즐 판 | N×N 셀 (4×4 ~ 7×7) | 스테인드글라스 창틀 |
| **셀(Cell)** | 최소 단위 | 정사각 유리 조각 | 반드시 어떤 영역에 속해야 함 |
| **색점(Seed)** | 영역의 씨앗 | 셀 위의 색 원 + 크기 숫자 | 영역당 정확히 1개 |
| **납선(Seam)** | 셀 사이 경계벽 | 셀과 셀 사이 선분 | 혼자 탭해서 토글 |
| **이중납선(Double Seam)** | ★협동 A | 굵은 금색 선분, 양 끝 앵커 2개 | 두 손가락 **동시 탭** |
| **긴납선(Long Seam)** | ★협동 B | 3칸 이상 연속된 굵은 선 | 양 끝 **동시 홀드** |
| **잠긴영역(Locked Region)** | ★협동 C | 자물쇠 표시된 색점 | 한 명이 **누르고 있어야** 편집 가능 |
| **단서패널(Clue Panel)** | 크기 힌트 표시 | 화면 위/아래 가장자리 | 양쪽 **동일 내용**, 각자 방향으로 회전 |

색점 색상 5종: 🔵파랑 · 🔴빨강 · 🟡노랑 · 🟢초록 · 🟣보라

## ② 퍼즐 규칙

납선을 긋고 지워서 격자 전체를 영역들로 나눈다. **아래 3개를 전부 만족하면 완성.**

1. **모든 영역은 색점을 정확히 1개 포함한다** (0개도, 2개도 안 됨)
2. **영역의 크기(셀 수) = 그 색점에 지정된 숫자**
3. **모든 셀은 어떤 영역에 속한다**

> 실제 스테인드글라스 제작(납선으로 유리 조각을 나눔)과 그대로 대응한다. 테마가 장식이 아니라 규칙 그 자체.

**패배 없음.** 시간 제한·실패·점수 없음. 납선은 언제든 다시 눌러 지울 수 있다. 부부가 편하게 하는 게임이라 **완성 화면만 존재한다.**

**힌트는 양쪽에 똑같이 보인다.** 위/아래 패널은 같은 내용을 각자 방향으로 회전해 보여줄 뿐이다 (읽기 편하라고 두는 것이지 숨기는 게 아니다).

## ③ ★ 협동 조작 3종 (이 게임의 핵심)

셋 다 **혼자서는 물리적으로 불가능**해야 한다. 공통 강제 조건:

- 서로 다른 `pointerId`여야 함 (같은 손가락의 순차 입력은 무효)
- **두 접점 사이 거리 ≥ 화면 대각선의 35%** — 혼자 두 손으로 하는 걸 막는다
- 퍼즐마다 해답에 **반드시 필요한 위치**에만 배치 (장식용 금지)

### A. 이중납선 — 순간을 맞추기
양 끝 앵커를 **250ms 이내에 동시 탭**하면 토글된다.
- 한쪽만 눌리면 그 앵커가 맥동(pulse)하고 반대쪽 앵커에 화살표가 떠서 "여기 눌러" 신호를 준다
- 250ms를 넘기면 대기가 풀린다 → "하나, 둘, 셋!" 하는 순간이 생긴다

### B. 긴납선 — 같이 힘주기
3칸 이상 연속된 긴 납선. 양 끝을 **동시에 누른 채로 800ms 유지**하면 선이 양쪽에서 자라나 가운데서 만나며 완성된다.
- 진행 게이지가 선을 따라 차오른다 (시각적 보상)
- 중간에 한 명이라도 손을 떼면 **되감긴다** → 둘 다 버텨야 하는 긴장
- A가 순간 타이밍이라면 B는 지속 — 결이 다르다

### C. 잠긴영역 — 잡아주기
자물쇠가 달린 색점. 그 영역의 납선은 기본적으로 편집이 안 된다.
- **한 사람이 색점을 누르고 있는 동안에만** 그 영역의 납선이 열린다
- 누르고 있는 사람은 손가락이 묶여 있어 **본인이 편집할 수 없다** → 반드시 상대가 조작해야 함
- 셋 중 대화를 가장 많이 만든다: "잡았어" "여기? 아니 그 옆"

| 조작 | 성격 | 필요한 것 |
|---|---|---|
| A 이중납선 | 순간 동기화 | 타이밍 |
| B 긴납선 | 지속 동기화 | 인내 |
| C 잠긴영역 | 역할 분담 | 소통 |

## ④ 퍼즐 공급 · 난이도 곡선

적이 없는 게임이므로 "컴퓨터가 하는 일" = 퍼즐을 내주는 것.

| 단계 | 격자 | 영역 수 | 협동 조작 | 목표 소요 |
|---|---|---|---|---|
| 튜토리얼 1~2 | 4×4 | 3 | 없음 (규칙 익히기) | 1분 |
| 튜토리얼 3~4 | 4×4 | 3 | A만 | 2분 |
| 쉬움 5~8 | 5×5 | 4 | A, B | 3분 |
| 보통 9~14 | 6×6 | 5 | A, B, C | 5분 |
| 어려움 15~18 | 7×7 | 5~6 | A, B, C 다수 | 8분 |

### 유일해 보장 — 생성기는 쓰되 런타임에는 없다

**유일해가 아니면 "논리적으로 맞게 풀었는데 오답"이라는 최악의 경험이 난다.** 그래서:

1. **개발 시점에** 생성기(`scripts/genpuzzles.js`)가 랜덤 분할로 후보를 대량 생성
2. 각 후보를 **완전탐색 검증기**에 넣어 해가 **정확히 1개**인지 확인
3. 통과한 것만 골라 `js/puzzles.js`에 **정적 데이터로 박아 넣는다**
4. **런타임에는 생성기가 없다** → 플레이 중 유일해가 아닌 퍼즐이 나올 가능성 0

즉 손으로 18판을 짜는 대신 검증된 파이프라인으로 뽑되, 게임에는 검증 통과한 결과물만 실린다. (7×7 완전탐색은 가지치기하면 충분히 빠르다)

## ⑤ 조작 체계

**입력은 멀티터치 전용.** 마우스는 개발·디버그용으로만 동작.

| 동작 | 조작 |
|---|---|
| 일반 납선 긋기/지우기 | 셀 경계를 한 번 탭 (토글) |
| 이중납선 (A) | 양 끝 앵커를 동시 탭 (250ms 이내, 다른 `pointerId`) |
| 긴납선 (B) | 양 끝을 동시에 800ms 홀드 |
| 잠긴영역 (C) | 한 명이 색점 홀드 → 상대가 그 영역 납선 편집 |
| 영역 미리보기 | 셀을 길게 누르기(500ms) → 속한 영역 하이라이트 |
| 되돌리기 | 각 패널의 ↺ 버튼 (양쪽에 하나씩) |
| 다음/이전 퍼즐 | 완성 후 나타나는 버튼 |

### ⚠️ 멀티터치 필수 처리 (안 하면 반드시 터짐)

1. **`touch-action: none`** — 없으면 브라우저가 터치를 스크롤로 가로챈다
2. **`user-scalable=no`** — 두 손가락이 가까우면 핀치줌으로 오인식한다
3. **Pointer Events 사용** (`pointerdown/move/up/cancel`) — 마우스와 통합돼 디버그가 쉽다
4. **`pointerId`로 손가락 구분** — 협동 판정의 전제. 같은 `pointerId`가 두 지점을 누른 건 **동시로 인정하지 않는다**
5. **`pointercancel` 처리** — 전화·알림이 오면 터치가 취소된다. 대기 중이던 앵커·홀드를 반드시 해제해야 유령 상태가 안 남는다

### 마주 앉기 (화면 방향)

폰을 **가로로 눕혀 두 사람 사이에 놓는다.**
- 아래쪽 = 플레이어 A 패널 (정방향)
- 위쪽 = 플레이어 B 패널 (180° 회전)
- 가운데 = 공용 격자

**격자 위에는 숫자를 쓰지 않는다** (한쪽에서 거꾸로 보이므로). 색점은 방향성 없는 원형이라 양쪽에서 똑같이 보이고, 크기 숫자는 각자 패널 안에서 자기 방향으로 읽힌다.

## ⑥ 화면 구성 (UI)

```
┌─────────────────────────────────────┐
│  [B 패널 — 180° 회전]                │  ← 아내 쪽
│  🔵4 🔴3 🟡5 🟢2 🟣4  / ↺ / 3-5 완성  │
├─────────────────────────────────────┤
│                                     │
│        공 용  격 자  (Canvas)        │
│   색점 · 납선 · 앵커 · 자물쇠 · 게이지  │
│                                     │
├─────────────────────────────────────┤
│  [A 패널 — 정방향]                   │  ← 내 쪽
│  🔵4 🔴3 🟡5 🟢2 🟣4  / ↺ / 3-5 완성  │
└─────────────────────────────────────┘
```

- 양 패널 **내용 동일** (회전만 다름)
- **완성 연출**: 납선이 금색으로 빛나고 각 영역에 유리 질감·빛 투과가 채워진다 (`game-texture` 스킬)
- **협동 대기 표시**: 앵커 맥동 / 긴납선 게이지 / 잠금 해제 글로우
- **패배 화면 없음**

## ⑦ 완료 기준 (체크리스트) ★

각 항목은 `self-check` 스킬에서 테스트 하나가 된다.

### 퍼즐 로직 (headless — DOM 없이)
- [ ] 납선을 토글하면 영역 분할이 즉시 재계산된다
- [ ] 규칙 3개를 모두 만족하면 완성 상태가 `true`가 된다
- [ ] 색점 0개인 영역이 있으면 완성이 `false`다
- [ ] 색점 2개 이상인 영역이 있으면 완성이 `false`다
- [ ] 영역 크기가 색점 숫자와 다르면 완성이 `false`다
- [ ] **18판 전부 해가 정확히 1개다** (완전탐색 유일해 검증)
- [ ] 18판 전부 정답 배치를 넣으면 완성 판정이 뜬다
- [ ] 되돌리기가 직전 상태로 정확히 복원한다

### 협동 조작
- [ ] 이중납선은 앵커 하나만 눌러서는 토글되지 않는다
- [ ] 다른 `pointerId` 두 개가 250ms 이내에 양 앵커를 누르면 토글된다
- [ ] 같은 `pointerId`가 양 앵커를 순차로 눌러도 토글되지 않는다
- [ ] 251ms 이상 벌어지면 토글되지 않고 대기가 해제된다
- [ ] 긴납선은 800ms 동안 양쪽이 유지돼야 완성된다
- [ ] 긴납선 도중 한쪽이 손을 떼면 게이지가 되감긴다
- [ ] 잠긴영역은 색점을 누르고 있지 않으면 납선이 편집되지 않는다
- [ ] 잠긴영역의 색점을 누른 그 손가락으로는 납선을 편집할 수 없다
- [ ] `pointercancel`이 오면 대기 중인 앵커·홀드가 전부 해제된다
- [ ] 모든 협동 조작의 두 접점 거리가 화면 대각의 35% 이상이다
- [ ] **협동 조작을 쓰지 않고는 어떤 퍼즐도 완성할 수 없다** (필수 경로 검증)

### 입력·화면
- [ ] 두 손가락이 서로 다른 셀 경계를 동시에 눌러도 둘 다 정상 처리된다
- [ ] 격자 위에 숫자가 하나도 렌더링되지 않는다
- [ ] B 패널이 180° 회전된 상태로 렌더링된다
- [ ] 페이지에서 핀치줌·스크롤이 발생하지 않는다
- [ ] 퍼즐 완성 시 완성 연출과 다음 퍼즐 버튼이 나타난다

### 품질
- [ ] 브라우저 콘솔에 에러·경고가 0건이다
- [ ] 실제 폰에서 두 사람이 1판을 끝까지 완성할 수 있다 (실기기 확인)

## 성능 상한

2D Canvas 게임이라 3D의 draw call 대신 다음을 예산으로 잡는다.

| 항목 | 상한 | 지키는 법 |
|---|---|---|
| 목표 프레임 | 60fps (최악 장면 55 이상) | 아래 준수 시 자연 달성 |
| 최악 장면 | 7×7 격자 + 동시 터치 4점 + 긴납선 게이지 + 완성 파티클 120개 | 이 장면에서 측정 |
| 프레임당 그리기 | ≤ 8ms | 격자는 정적 레이어로 캐시, 변하는 것만 매 프레임 |
| 캔버스 레이어 | 3장 (배경 격자 / 납선·색점 / 연출) | 배경은 한 번만 그리고 재사용 |
| 텍스처 | 1k 유리 타일 3~4종 | `game-texture` 스킬, 절차적 생성 폴백 |
| 상태 재계산 | 납선 토글당 1회, ≤ 2ms | flood fill, 7×7=49셀이라 저렴 |

파티클이 예산을 넘으면 정밀도를 올릴 게 아니라 **개수를 줄인다.**

## 기술 구조

- **빌드 도구 없음.** 단일 `index.html` + ES 모듈. `python3 -m http.server`로 바로 실행
- **2D Canvas.** Three.js 불필요 (격자 퍼즐에 3D는 과잉)
- **GitHub Pages 정적 호스팅** + PWA (홈 화면 설치)
- 고정 타임스텝 루프는 연출·게이지용. 퍼즐 로직은 이벤트 구동

### ★ 로직 / 입력 분리 (원격 모드 대비)

```
입력(input.js) → 의도(intent) → 로직(puzzle.js) → 렌더(render.js)
                    ↑
              여기에 네트워크를 끼우면 그대로 원격 협동
```

`puzzle.js`는 **오직 intent만 받아 상태를 바꾼다.** 브라우저 API를 일절 참조하지 않으므로:
1. Node에서 브라우저 없이 테스트된다 (`self-check`의 headless 시뮬레이션)
2. intent를 WebRTC/PeerJS로 보내면 **로직을 한 줄도 안 고치고** 원격 협동이 된다

## 2차 확장 — 각자 폰 모드에서 비로소 열리는 것

원격은 "떨어져 있을 때의 편의"가 아니라 **정보 비대칭이라는 메커니즘을 여는 열쇠**다. 각자 화면이 생기면 한 폰에선 불가능했던 게 진짜가 된다.

| | 한 폰 (MVP) | 각자 폰 (2차) |
|---|---|---|
| 협동의 축 | 손이 모자람 | 정보가 모자람 |
| 체감 | 손발 맞추기 | 말로 맞추기 |
| A/B/C 조작 | ✅ | 완화 규칙 필요 (동시성 → 양쪽 활성화) |
| 정보 비대칭 | ❌ | ✅ A는 크기만, B는 배치 제약만 |

**두 모드는 사실상 다른 게임이다.** 한 폰 버전을 먼저 만들어 실제로 해보고, 재밌으면 그때 각자 폰 모드를 얹으면서 정보 비대칭을 진짜로 넣는다.
